# Ledger-driven development (LDD)

LDD preserves a strict role split:

- **Architect/controller** owns intent, recon, decisions, specifications, unit boundaries, verification, integration sequencing and the ledger.
- **Workers** write production code using the normal `flow-execution` model.

While LDD is active, the architect **never writes production code**, including tiny corrective edits. It routes corrections through the existing unit owner or another bounded worker. This keeps the long-lived context about why/what, not implementation minutiae.

The durable authority lives under `.flow/ldd/<epic>/`. Do not use `.omp/` for LDD state; `.omp/` has configuration/discovery semantics.

## Authority boundary

The ledger owns durable **project truth**: accepted product/architecture decisions, contracts, traps, verified facts, unit state and unresolved questions.

The current Flow/OMP stack owns **execution mechanics**: agent transport, mailbox vs Hub, isolation/workspace policy, model routing, verification layering and task lifecycle. Historical ledger/handoff instructions about those mechanics are version-sensitive evidence, not permanent authority; revalidate them against the current stack when resuming. Static planning handoffs from ChatGPT/another harness are also evidence/proposals until reconciled into the current ledger. Explicit current user instructions outrank both.

## External planning intake

When the user brings a ChatGPT/other-harness planning bundle into an epic, first use the `flow-external-session` planning-handoff protocol. Validate its manifest, observed repository revision, local dirty state and current ledger. Do not copy a proposed ledger delta/unit into canonical state blindly; reconcile it, record accepted decisions/contracts, and preserve conflicts/open questions explicitly. A handoff does not carry local implementation authorization.

Do not make the user repeat already-settled design choices merely because they were decided in another session. Reopen only a fork whose assumptions are stale, contradicted, unapproved, or materially incomplete. Preserve a current external strategy even when it is not yet execution-grade. If the bundle's plan satisfies the current `flow-planning` execution-grade contract, do not repeat planning; otherwise refine only the missing consequential HOW/tests/interfaces instead of reopening settled WHAT/WHY.

## Loop

1. **Re-orient cheaply** — start with the current RESUME snapshot, git branch/status/diff, active unit contract, and only the exact active plan/task/receipt paths named by the forward pointer. Do not read the whole `PLAN.md`, ledger history or prior task files by default. Expand outward only when the resume pointer is incomplete/stale, source reality contradicts it, or a consequential verification claim requires older context. Agent Hub/history is execution evidence; the ledger is current project truth.
2. **Bootstrap** (new epic) — choose local vs shared ledger mode with the user and create `references/ledger-skeleton.md`.
3. **Recon** — verify inherited claims at source. For broad recon spanning separable subsystems/historical sources, prefer bounded parallel read-only `scout` tasks for extraction/mapping; the architect synthesizes centrally and independently checks consequential facts. Do not spawn scouts for trivial recon.
4. **Decide** — resolve product/architecture forks with the user. Use `flow-design` for a material decision. Lock the result in the ledger.
5. **Specify unit + approve WHAT** — write the unit contract: behavior, boundaries, dependencies, acceptance criteria, traps and verification expectations. This is the WHAT/authority boundary, not an excuse to delegate consequential HOW to an implementer. Present the completed contract's meaningful behavior/boundary/acceptance summary and obtain **explicit user approval** before dispatching `flow-planner` or otherwise treating the contract as approved. A unit-start/resume command does not create missing approval. Reuse a recorded prior contract approval while the approved contract is materially unchanged; a material WHAT/boundary/acceptance change reopens this gate.
6. **Plan consequential HOW + approve execution** — only after contract approval, when the unit would otherwise require implementation judgment, use `flow-planning`. For substantial LDD consequential HOW that is not already covered by a current validated external execution-grade plan, dispatch a dedicated `flow-planner` (`@plan`) to own plan recon/writing; Main consumes its compact receipt and owns plan acceptance rather than authoring the substantial plan itself. Create an execution-grade `PLAN.md` + fresh-executor task briefs. When the plan is ready, present its dependency shape, important locked decisions, proof strategy and residual risks, then obtain **explicit plan approval** from the user before any production-writing worker is dispatched. That approval authorizes local implementation only within the approved plan envelope; publication remains separately gated. A material HOW/scope change outside that envelope reopens the plan gate, but normal task rotation and in-plan correction do not. A tiny/obvious unit may skip a separate plan, but contract approval still does not authorize implementation: obtain explicit local implementation approval before the first production-writing worker. A current validated external execution-grade plan may satisfy the planning artifact stage, but it still carries no local implementation authorization.
7. **Authorize/dispatch** — only after the required approval(s) are recorded, use `flow-execution`: each execution-grade task is normally non-isolated on the same suitable feature checkout but gets one **fresh** `flow-plan-executor` (`@execute`), sequentially unless tasks are truly independent; unresolved semantic/debugging work → persistent `flow-implementer` (`@task`); exact mechanical leaves → `sonic`. Independent top-level writers may run isolated/concurrently. External top-level session/other harness → `flow-external-session`.
8. **Clarify/continue live** — plan executors escalate contradictions instead of redesigning; semantic owners resolve local uncertainty and ask Main only when the contract/design boundary moves. If a plan executor hits OMP's soft/request-budget warning or repeated same-blocker churn, it yields with exact state/proof and Main starts a fresh task/correction owner rather than driving it into force-stop. A genuinely new decision returns through `flow-planning`/`flow-design`/user approval. Never wait merely to observe **or collect completion from** a running worker: record the pending dependency, return foreground control, and remain interactive. Ordinary child completion must not cause a `hub wait` merely because no sibling work is runnable. The runtime orchestration guard blocks interactive Main's bare/job `hub wait`; named process waits and targeted peer-reply waits remain available. Treat a guard block as a yield-to-foreground signal, never something to bypass with polling.
9. **Verify/accept** — consume compact worker/reviewer receipts first, then inspect actual patches and consequential integration evidence. For execution-grade planned work, use one strong `flow-acceptance-reviewer` after the coherent implementation rather than routine COR/TTC/CRF fan-out; it checks both plan conformance and independent correctness. **Acceptance review is a dependency barrier** for expensive downstream evidence: while a required acceptance/closure review or correction that can change the evidence surface is unresolved, Main remains interactive but does not start device/emulator/manual/external acceptance evidence. Consume the review completion event, resolve material findings/corrections, and refresh affected automated proof before crossing that gate. Worker self-verification is required and architect verification remains additive.
10. **Correct efficiently** — verify/deduplicate material findings, batch them into one correction round, route in-plan fixes through a fresh bounded plan executor, semantic fixes to the persistent semantic owner, and plan defects back through `flow-planning`. Use one scoped acceptance closure review by default rather than restarting all lenses.
11. **Checkpoint/record** — append decisions/results, status, verification receipts and a fresh RESUME snapshot that names the exact next plan task/action; preserve unresolved hazards/deviations. **Before the first device/emulator/manual/external acceptance action**, write a durable recovery checkpoint with exact head/tree, dirty/user-owned state, fresh evidence already accepted, remaining criteria, external/device state and next action. For **multi-step device/manual acceptance**, Main must delegate environment operation/evidence capture to fresh bounded `flow-evidence-verifier` (`@vision`) capsules when that agent is available; Main owns the checkpoint, acceptance brief, consequential evidence inspection and final judgment rather than driving the sequence itself. A trivial single read/observation may stay with Main. One coherent scene/state/acceptance cluster belongs to each verifier session. Before each verifier dispatch, write an `Evidence capsule:` manifest in the task brief with `ID`, `Owns`, `Independent split check`, `Excludes`, and `Restore obligation`; the runtime guard rejects missing manifests and the verifier rejects semantically separable bundles before tool use. Different acceptance modalities/operators are separable by default: shared device/save/setup state is not sufficient evidence of inseparability, and automated capture/proxy evidence stays separate from physical human-operated/manual/assistive-technology interaction unless one genuinely cannot be restarted or reached independently. Independent scene families or operator/modalities get fresh sessions sharing durable artifacts/environment state, not transcript context. A restore-bearing receipt records `before`/`after` identity or hashes and MATCH/MISMATCH/UNKNOWN; `MATCH` is valid only when the rendered before/after values self-consistently agree under the same comparison scheme, otherwise the receipt must be corrected or report `UNKNOWN`. Already-proved restoration is not re-investigated without a freshness reason.
12. **Prepare context rotation when useful** — an active Main cannot rotate itself. After a durable phase boundary such as accepted planning → execution supervision or coherent implementation → device/integration verification, if quota/context pressure makes a fresh controller worthwhile, ensure RESUME is sufficient and provide a terse top-level resume handoff. Continue the current session unless the user/harness actually starts a fresh controller; do not manufacture a restart as ceremony or a new approval gate.
13. **Integrate** — sequence accepted units; external publication/merge stays user-owned (`flow-integrating`).

## User-facing continuity

The architect maintains a **forward pointer** across sessions and checkpoints. After a recon result, locked decision, accepted unit, correction, or ledger update, briefly state what is now true, what the architect will do next, and whether the user must decide/approve anything. If the next step is determined by this loop and already authorized, proceed without asking the user to choose it. At a real approval/design/integration gate, ask the concrete question immediately instead of reporting status and stopping.

## Ledger boundary

The ledger is not a backlog and not a transcript. Weft remains the durable human/project backlog. The ledger holds only what a future architect needs to continue the epic correctly: current state, locked decisions/rejected alternatives, cross-unit contracts, traps, open questions, unit status, verification receipts and corrections to previous assumptions.

Worker transcripts/patches/PR discussions are evidence linked from the ledger, not copied wholesale into it.

## Coordination hierarchy

1. Same OMP session/task agents → Agent Hub/`hub`, `history://`, `agent://`.
2. Optional Vibe director mode when persistent worker conversations are specifically useful; remember it is a different session mode, not a requirement of LDD.
3. Independent top-level session/other harness → `flow-external-session` static planning/worker handoff; mailbox only when durable two-way asynchronous conversation is actually needed.

Never create a filesystem mailbox around ordinary OMP child agents.
