# OMP compatibility assumptions

This stack's v8 trial assumptions were revalidated against the public `can1357/oh-my-pi` main branch at commit `9b2a43514bfcfc0b9607ac9ac160115aec897f06` (2026-09-14). Anthropic profile selectors and adaptive-effort support were additionally re-checked against `a2501722aa05670eeab327ea1325e3fde55e51a9` / OMP 18.1.21 (2026-09-14). Agent Hub wait behavior was re-checked against OMP 18.1.22 (`23a5b9a`, 2026-09-14), whose unified waits use an adaptive window while remaining interruptible through the normal tool-abort/steering path. Extension tool approval policy (`policy: prompt` / `deny` under yolo), `formatApprovalDetails`, essential custom tools, and fail-closed `tool_call` interception were re-checked against OMP 18.2.10 (`da58b16`, 2026-09-22). OMP moves quickly; re-check these assumptions when upgrading across substantial releases.

The design relies on these native behaviors:

- named profiles (`omp --profile <name>`) relocate the whole OMP-native user root to the profile-specific agent directory and do not inherit the default profile config;
- user skills are discovered from the active agent directory `skills/*/SKILL.md`;
- user task agents are discovered from `agents/*.md` and may bind arbitrary custom `modelRoles` aliases plus `autoloadSkills`; v8 uses `@execute` in addition to OMP's conventional roles;
- user rules are discovered from `rules/*.{md,mdc}`, including `alwaysApply`;
- user TypeScript/JavaScript extensions are auto-discovered from `extensions/`;
- custom extension tools can declare explicit `policy: prompt` / `deny` approval decisions that remain authoritative under yolo, can add `formatApprovalDetails`, and can be kept `loadMode: essential`; Flow uses this for the interactive `flow_gate` artifact-approval boundary rather than transcript parsing;
- extension `tool_call` interception is fail-closed and sees `task` inputs before execution, so Flow can reject stale/missing governance manifests without replacing OMP's task/Hub implementation;
- OMP raises a desktop notification for the `ask` tool but not for a tool approval prompt (OMP 18.4.12, unchanged in 18.5.0). It emits `tool_approval_requested` to extensions before it shows the prompt, and extension imports of `@oh-my-pi/pi-tui` resolve to the host instance. The governance guard uses both to send `TERMINAL.sendNotification` when `flow_gate` waits for approval, titled with the session name so a background session is identifiable; `PI_NOTIFICATIONS=off` silences it like any OMP notification. The approval dialog paints every `formatApprovalDetails` line in the theme accent and drops empty lines, so `flow_gate` structures its details with bold/dim escapes (which keep the accent colour) and single-space spacer lines;
- `tool_call` events carry the tool input before execution; for a hashline `edit`, OMP adds the header targets as `path`/`paths` (`src/extensibility/tool-event-input.ts`, OMP 18.4.5). The governance guard blocks `write`, `edit` and `ast_edit` on any `.flow/runtime/` path, reading `path`/`_path`, `paths`, patch-mode `edits[].rename` and the header lines of a raw hashline, apply_patch or sloppy `input`/`_input`, after resolving symlinks. It also blocks a write whose resolved path is at or below the real `.flow/runtime` directory, so a symlinked `.flow` or `.flow/runtime` does not hide it. A target with a URL scheme other than `file:` (`ssh://localhost/<repo>/%2Eflow/runtime/gates.json`) is tested on its percent-decoded path; an undecodable escape blocks. The same file tools may not write under `.git/` (the directory, or the gitfile of a linked worktree plus the common git directory it names), because repo-local git config, attributes and excludes feed the acceptance fingerprint. `bash` is blocked when its `cwd` lies inside `.flow/runtime/`: OMP matches `bash.patterns` on `command` only and honours `cwd` at execution. Not blocked: writes through the `bash` command text (see the prompt rule below), `eval` or any other tool. There only the `flow-artifacts` rule protects `.flow/runtime/`;
- `ast_edit` expands its `paths` as follows (OMP 18.4.5, `tools/ast-edit.ts` calling `resolveToolSearchScope` in `tools/path-utils.ts`, then the native `astEdit`, whose Rust source is not shipped, so the walk was measured on the installed build). An entry may pack several targets with `;`, `,` or whitespace outside braces (`expandDelimitedPathEntries`). Each target splits at its first segment holding `* ? [ {` into a base and a glob (`parseSearchPath`). The walk rewrites every file below the base whose language the extension names (JSON included; with an explicit `lang`, any file), hidden directories too, and only files whose path relative to the base matches the glob: `*` stays inside one segment, `**` crosses segments, a bare `*.json` matches the top level only, and a glob that matches only a directory rewrites nothing. It does not follow symlinks met inside the walk, but follows a symlinked base. It honours `.gitignore` and the primary checkout's `.git/info/exclude`, but **not** the common-dir exclude seen from a linked worktree (measured: a `/.flow/` entry hides `.flow/` in the primary checkout and not in a linked one). The guard therefore never relies on the exclude entry: it blocks an `ast_edit` call when a file that exists under `.flow/runtime/` (at the working directory, the repository root, or at or above a base) lies below a target's base and matches its glob. `.` and `**/*.json` are blocked once gate state exists; `src`, `src/**/*.ts` and `**/*.ts` pass. An entry it cannot read (an unclosed `[` or `{`, a non-string entry, a non-array `paths`, an unreadable runtime directory, more than 10000 files there) is blocked, and so is a call with no `path`, `_path` or `paths` target, which would walk the working directory. The walk skips every `.git` directory and gitfile below its base (measured, nested ones included) and reaches git state only from a base at or inside `.git`, so only such a base is blocked. Residual: a `.flow/runtime/` below a directory target that is neither the working directory's, the repository root's nor an ancestor-or-self of the base (a nested checkout) is not looked for;
- OMP splits a raw target at its first glob segment first, then normalizes only the base with `expandPath` (`tools/path-utils.ts:72-130`); the glob stays raw. `expandPath` drops a stray leading `:` before `/`, `~`, `./` or `../` (models emit it intermittently), drops `@` before `/` or `~`, decodes a `file://` URL with `fileURLToPath` (`localhost` and percent-escapes such as `%2Eflow` included), and expands `~`. The guard follows the same order with one helper (`expandToolPath`) for the base of an `ast_edit` target and for the literal paths of `write`, `edit` and `ast_edit`, so `@<dir>`, `:<dir>`, `:./`, `file://localhost<dir>`, `file://<dir>/%2Eflow` and `file://<dir>/.flow/r?ntime/*` resolve as they do in OMP (a `?` in a `file:` glob is a glob character, not a URL query). It differs where OMP would read something else than the URL says: an undecodable file URL (OMP keeps it as a literal path) and a `file:` base that still holds `?` or `#` after the split (the decoder would drop everything after it) both block the call;
- the governance guard's acceptance fingerprint hashes `git diff --binary --no-ext-diff --no-textconv HEAD`, then the staged diff (`git diff --cached …`) as its own `staged` section, then the untracked files. Diff drivers (`diff.external`, textconv) never shape it, and a change staged then reverted in the working tree still changes it. Acceptances recorded before the staged section was added read stale once and need one more `flow_gate accept`;
- Plan mode is read-only and owns plan approval/execution semantics;
- task batches support per-item agents and optional per-spawn isolation when `task.isolation.enabled` is on;
- task model selection comes from agent overrides/frontmatter roles rather than a per-call model field;
- headless subagents cannot prompt for approvals, so Flow constrains writer authority in the task contract and verifies results at the controller;
- child agents can coordinate with their parent/Main through `hub`; ordinary non-isolated agents are revivable after parking, while completed isolated task runs are torn down and are not revivable; unified Hub waits wake on watched job completion or peer messages and are interruptible by user steering, so a wait parks the current autonomous run without preventing the user from prompting; ordinary task results may also self-deliver, and `send` can await one peer reply, so a revived owner is awaited with `hub send` `await: true` or a peer-filtered reply wait, never through its old job id; Flow leaves native wait/steering semantics intact, does useful independent work first, may wait when the next meaningful action depends on the result, and avoids progress polling; targeted peer-reply waits remain available for bounded request/response cases;
- nested agents are depth-gated by OMP; `flow-implementer` intentionally restricts nested spawning to bundled `scout` and `sonic`;
- Agent Hub/history/agent artifacts are execution records, not replacements for committed `docs/decisions/` records;
- bundled `reviewer` handles ordinary correctness review, while security review/scan remains OMP-native; Flow may bind its planned acceptance reviewer to `@slow`;
- ordered `bash.patterns` support explicit `prompt` rules that remain effective under yolo. The matcher (`packages/coding-agent/src/tools/bash.ts` at `78b7531`, OMP 18.2.6, 2026-09-18) trims and whitespace-collapses the pattern, turns each `*` into `.*` with every other character literal, anchors at both ends, and is case-sensitive; `prompt`/`deny` rules fire on the whole command or any segment of a compound line, and the first matching rule wins. `tests/bash-patterns.test.mjs` ports that matcher. Known residuals: a bare environment assignment (`GH_TOKEN=x gh api …`, `FOO=1 git push`), a bare `env` with no assignment before the command, `env … git -C … push`, `git --git-dir=… push` and wrappers (`sudo`, `xargs`, `sh -c`, `command`) do not match the anchored patterns; the semantic rule in `flow-safety` still governs them. In the other direction, `git -C * push*`, `git -c * push*` and `env * gh *` also prompt when ` push` or ` gh ` appears later in an unrelated command, such as a commit message, and `env * gh *` prompts for `gh` reads. The baseline intentionally leaves blanket `tools.approval.eval` prompting unset because it creates excessive friction for ordinary eval use; stakeholder-visible publication actions must stay on the direct guarded Bash surface rather than being wrapped in eval. Headless subagents cannot satisfy a direct publication prompt and therefore fail closed on those explicitly prompted commands;
- the `*.flow/runtime*` prompt rule makes any direct Bash line or segment that names `.flow/runtime` ask first, in all three profiles. This list is the single home of its residuals; other documents point here. It matches by text, so these are not covered: a path assembled from pieces (`cd .flow && … runtime/gates.json`, quoted fragments), `.flow//runtime` and `.flow/./runtime`, a shell-quoted spelling such as `$'\x2eflow/runtime'`, name-based selection (`find .flow -name gates.json -delete`), a write to `.flow` as a whole (`cp -r`, `mv`, `rm -rf .flow`, `tar`), a hard-linked copy of gate state (`cp -al .flow …`, which a later file-tool write reaches through the shared inode), a shell glob for the directory name (`.flow/r*/gates.json`) and eval writes; the `flow-artifacts` rule still governs them. The `cwd` argument, which the rule never sees, is blocked by the hook when it lies inside `.flow/runtime/`; a leading `cd <path> &&`, which OMP turns into `cwd` at execution, and a `cwd` of `.flow` with a relative `runtime/…` path in the command stay with the text rule. The same holds for `.git/`: file tools are blocked there, while bash and eval writes to repo-local git config, attributes or excludes are residual and no prompt rule covers them. The user-global layer (`~/.gitconfig`, `$XDG_CONFIG_HOME/git/{config,attributes,ignore}`) also feeds the fingerprint through `filter.*.clean`, `core.attributesFile` and `core.excludesFile`; no tool is blocked there, because editing the user's own git configuration is a legitimate request;
- the first-party Anthropic provider exposes `claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`, and `claude-fable-5-1` with adaptive effort `low`/`medium`/`high`/`xhigh`/`max`;
- Anthropic OAuth credentials are profile-local under named profiles; the repository never stores Team credentials.

## Upgrade smoke test

After upgrading OMP:

```sh
./tests/run.sh
./scripts/omp-stack doctor
```

Then sanity-check `omp --profile openai-codex`, `omp --profile ollama-cloud`, and `omp --profile anthropic`.

Then sanity-check in OMP that `flow-planner`, `flow-plan-executor`, `flow-acceptance-reviewer`, `flow-implementer` and the Flow skills are discoverable; confirm `@execute` resolves per profile, publication Bash commands prompt, and an isolated test task exposes the `isolated` field. Do not paper over a changed OMP contract inside skills; update the native boundary deliberately.
